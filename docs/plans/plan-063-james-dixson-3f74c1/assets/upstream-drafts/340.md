**Fixed by plan-063 (Epic 1 + Epic 2). Closing.**

The crash itself was a one-line arity mismatch: `_worktree_teardown(plan_dir, force)` takes two
parameters and L18 called it with one. But a one-line patch would have shipped two further
defects and left the underlying class open, so plan-063 fixed four things.

**1. The crash (`REQ-LAND-031`).** L18 now calls
`_worktree_teardown(ctx.plan_dir, force=False)` — **keyword form**, so the next signature change
fails loudly rather than silently rebinding a positional. `force=False` is confirmed against the
CLI path and is the only value consistent with INV-1 (teardown refuses on a dirty tree).

**2. A duplicate delete that would have become a PERMANENT false failure.** L18 also issued its
own `git branch -d`, after `_worktree_teardown` had already deleted the branch. Measured: once
the arity was fixed, L18 would report its own headline action as
`{"action": "delete-execute-branch", "ok": false, "detail": "branch not found"}` on **every**
landing, forever. The delete is now delegated, and the report reads the teardown's own
`branch_delete` step. `test_l18_delegates_branch_delete` pins that the branch is still deleted;
`test_prune_is_strategy_aware` pins that no `branch -d` reaches `ctx.run`. Both, because "the
duplicate is gone" and "the branch is still deleted" are different claims.

**3. An unread status.** `_worktree_teardown` returns `{"status", "path", "branch", "steps"}` and
**never** an `"action"` key, so L18's `wt.get("action") or wt` always took the fallback and
nothing consulted `status` at all. A **`blocked`** teardown — dirty worktree, nothing removed,
branch left behind — reported `verdict: pass`. L18 now branches four ways: `ok` → pass, `blocked`
→ halting fail with **no journal advance**, `partial` → inconclusive, and **absent `status`** →
inconclusive. A landing must not report a prune it did not perform.

**4. The reason it was a traceback and not a report (`REQ-LAND-030`).** Step dispatch is now
fail-closed: an exception raised by a `LAND_EXECUTOR` step becomes a halting `inconclusive` row
with `journal: null`, and **the halted envelope is returned directly from the handler**. That
last part is load-bearing — `_land_execute`'s loop predicate is `verdict == "fail" and halting`,
so an `inconclusive` row *falls through* and the loop runs the next step. For L18 that was
invisible because L19 is next; for an early step the landing would have walked past a crash into
destructive work. `KeyboardInterrupt` / `SystemExit` are re-raised. Process exit is **1**, not 2.

The journal deliberately does **not** advance past a step that raised, so a resume re-enters the
same step and raises again until the cause is fixed. That is correct: advancing it would
manufacture the evidence `_land_resume_done` exists to refuse.

**How it was missed, and what now catches it.** A whole-module arity sweep found **1 defect in
252 functions**, so this was not a dead-code problem. The common thread is that **every
instrument was calibrated against the call site instead of the callee**: 4 of 78 monkeypatched
stubs faked `_worktree_teardown` with one parameter, including `land_rehearsal.py:140` — which is
mechanically why plan-060's rehearsal recorded `l18_prune: pass` on a code path that could not
run. All four are corrected, and `scripts/checks/check_mock_fidelity.py` now binds every stub
against `inspect.signature` of its target in the FAST and FULL validation tiers. It is the only
one of four candidate passes that would have caught this before the first real `--apply`, and no
type checker validates a stub against its target.

**Stated limit:** the check binds the **argument** axis only. Return shapes are outside it — and
the return shape was load-bearing here (see 3 above). That residue is filed separately.

# Draft comment — #140 (yf-okf: enforce OKF structure below the bundle root)

**Disposition: `partial`. #140 stays OPEN.**

plan-057 shipped the **index-depth half** as `REQ-OKF-012`:

- **Rule D** — for each subdirectory, count files **recursively**; at `<= K` (K = 10, a
  constant) enumerate them individually, above K emit a bare `sub/` stub. The recursive reading
  is normative and is what collapses `references/` (391 files) and `reviews/` (108 files) to
  stubs.
- **The durable bound is PER-DIRECTORY** — no subdirectory contributes more than K entries,
  measured at exactly 10 (`plan-049/references`). The previously quoted "max 30 entries per
  bundle" was an *empirical* corpus maximum with zero margin and has already moved to 39
  (plan-059), which is why it is not what the requirement asserts.
- **The inverse drift signal** — `reindex --check` now reports `missing` for a nested file the
  rule selects but the index omits. Drift was one-directional before: a listed file that
  vanished was caught, an unlisted file that appeared was invisible.
- **Corpus effect:** 32 bundles re-repaired; the boilerplate ratio over the frozen 25-bundle
  denominator went **0.6848 -> 0.3443** (427 described / 280 distinct / 147 repeated).

**What remains open, and why the issue is not closed:** `REQ-OKF-CHK-002` has no other tracker
home, and nested `index.md` generation is **deliberately not built** (plan-056 D-1) — 6 of 28
bundles already deepen the root index by hand and produce the corpus's only irreducible entries,
while #171's own measurement says 52% of subdirectories would receive a valueless listing.

Also fixed here, filed as #290: `okf.reindex_write()` crashed with `AttributeError` on any index
whose listing run contained interleaved prose (a blank line or a `## Subheading`) — measured on
4 of 33 index-bearing bundles, including the plan that commissioned the fix. The corpus gate was
green while the paired repair verb could not run.

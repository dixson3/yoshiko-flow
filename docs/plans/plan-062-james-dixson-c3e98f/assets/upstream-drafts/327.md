**Closed by plan-062.** `land --apply` now reaches `_land_execute`.

## What was wrong

`_land_execute` drove all fifteen `LAND_EXECUTOR` steps, advanced the journal and was
fail-closed — and it had **exactly one occurrence in `plan_manager.py`: its own `def`.**
`--apply`, the sole writing mode of the landing capability, returned an unconditional stub:

```
"the --apply executor is not implemented in this change-set"
```

So no plan could land through the intended path. plan-061 landed only because its L1–L19
sequence was walked by hand.

**No test could see it**, because every test drove `_land_execute` *directly*. That is the
#263 vacuous-check class at the **harness** level: a suite passing comprehensively over an
engine that no entry point invokes. plan-060's Epic 6 rehearsal caught a real journal bug this
way while being structurally unable to notice that nothing called the thing it was rehearsing.

## What changed

**The resume fix landed first, and the order was the point.** Wiring the seam without it would
have opened a window in which `--apply` worked and a resume still re-posted every reconcile
comment. Reversed, the resume fix is inert until something calls the engine.

- **`REQ-LAND-029` — a resume no longer re-executes completed steps.** The `resume_from` block
  contained `for key, _ in LAND_EXECUTOR: pass`; `done` was built from journal *phases*, named
  as though it held executor *step keys*, and **loaded nowhere**. Measured in a sandbox, a
  resume after a halt at L17 re-executed all fifteen steps from L0 — including `l6_push_one`
  and `l7_reconcile_writes`. `_land_resume_done()` now performs that translation, resolving
  **forward** for the three unjournaled keys (backward would mark `l3_validate_merged` done
  and push the merged tree unvalidated) and exempting `l0_lock_acquire` (the lock is released
  at L4, so a uniform skip would run unlocked and then unlink a lock it never acquired).
- **`REQ-LAND-028` — `land --apply` shall reach the executor.** A build whose CLI does not
  invoke `_land_execute` is now non-conformant, however comprehensively `_land_execute` itself
  is tested. The `--apply` branch reads the decision *after* the tty gate, branches on all four
  of `LandingJournal.recover()`'s actions, re-derives and re-checks the digest, and calls the
  executor with the journal's resume point.
- **The verdict is three-valued.** L8's and L12's `inconclusive` results are explicitly
  non-halting, so a landing can reach `L_DONE` carrying one; laundering that into `pass` is the
  coercion `REQ-LAND-012` forbids.

## The check that would have caught it

A seam-level test, **authored before the wiring and recorded as failing against the unwired
build** (3 failed / 48 passed at `a9e764b`; 51 passed once wired). It adds **no
production-reachable bypass**: the tty gate is monkeypatched in-process only, the real-process
gate-closed test is retained byte-for-byte unmodified, and a source-level `ast` assertion
proves `land_cmd` still *calls* the gate — the one gap a gate-stubbed test cannot see.

Writing the whole test block before the fix paid for itself: it exposed that one of the new
tests **passed vacuously** against the unwired build, because the stub emitted
`inconclusive`/exit 2 on its own without ever reaching the executor. That is the same #263
class, inside the very file written to close it. It now carries a call-recording guard.

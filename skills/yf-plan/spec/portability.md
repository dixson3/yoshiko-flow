# Portability Specification

<!-- activation: 2026-04-05 -->

Plans are portable artifacts. A cold reader on a different machine, in a different repo, with no access to the drafting conversation, must be able to understand why a plan exists, what environment it assumes, what reviewers flagged, and what upstream issues it resolves — from the plan folder alone.

## Activation

REQ-PORT-ACT: The portability contract activated on **2026-04-05**. Plans whose first `scoping:` entry is on or after this date are subject to hard audit enforcement at intake. Plans whose first scoping entry is earlier are grandfathered: missing scaffolding yields `warn` findings instead of `fail`. Under the OKF-PLAN model the first `scoping:` date is read from the reserved bundle-root `log.md` — the oldest `## YYYY-MM-DD` date heading that carries a `scoping:` entry (REQ-DATA-012). For an un-migrated plan that still holds an in-`plan.md` `**Phase log:**` block, that legacy block is the fallback source, so grandfathered plans resolve identically before and after migration (SPEC REQ-OKF-MIG-002 preserves the first `scoping:` date across the extraction).
Rationale: Pre-existing plans in other projects must not be blocked from intake on their next use. The activation date lets new plans get full enforcement while giving existing plans a graceful migration path via `/yf-plan capture`. Relocating the phase log to `log.md` must not perturb this date, so the first-`scoping:` extraction is preserved by migration.
Verification: `plan_manager.py::PORTABILITY_ACTIVATION_DATE` matches the date in this file's activation header; `_plan_first_scoping_date` resolves the first `scoping:` date from `log.md` (with the legacy in-`plan.md` `**Phase log:**` as fallback).

REQ-PORT-ACT-OKF: The **OKF-PLAN scaffolding** checks — reserved `index.md` presence + listing shape (REQ-PORT-001) and the per-file `type`/`okf_spec` conformance floor (REQ-PORT-050) — are gated on a **second, orthogonal marker** in addition to the date grandfather: an **OKF-native marker**, defined as a parseable YAML frontmatter block on the bundle's `plan.md`. That block is present on a born-OKF (seeded) or a migrated plan and absent on a legacy one. A plan is **OKF-legacy** when it is date-grandfathered (first `scoping:` < activation) **OR** not OKF-native (no `plan.md` frontmatter). A missing-OKF-scaffolding finding is downgraded to `warn` for an OKF-legacy plan and is a hard `fail` **only** for an **OKF-native, non-grandfathered** plan. This gate is beyond the literal REQ-PORT-050/REQ-PORT-001 MUSTs and exists because the date grandfather (2026-04-05) does not cover the OKF surface: every one of the ~29 pre-adoption plans is scoped on or after the portability-activation date yet carries none of the OKF scaffolding, so a date-only rule would hard-fail all of them on their next audit. A migrated pre-activation plan is OKF-native (migrate stamps `plan.md` frontmatter) yet still date-grandfathered (migrate preserves the first `scoping:` date, REQ-OKF-MIG-002), so its migration gaps — e.g. a `README.md`-verbatim `index.md` that is not yet a listing — warn rather than fail. The dual-write consistency check (#8, REQ-DATA-015) and a non-zero review-count mismatch (REQ-PORT-006) are **not** gated this way: a frontmatter↔`**Field:**` divergence or an existing-files count mismatch is always a hard `fail`.
Rationale: OKF adoption must not retroactively block every existing plan from re-audit, exactly as the date grandfather protects pre-contract plans. Keying the downgrade on the presence of `plan.md` frontmatter (the migrate/seed artifact) — not the date — is what lets an un-migrated legacy plan pass with warns while an OKF-native plan is held to the full floor.
Verification: `_audit_plan` computes `okf_native = bool(plan.md frontmatter)` and `okf_missing_level = "fail" if (okf_native and not grandfathered) else "warn"`, applying it to the `index.md` (#1) and REQ-PORT-050 (#7) findings; `test_worktree.py::test_audit_legacy_bundle_passes_with_warns_only` (un-migrated → warn) and `test_audit_okf_native_missing_index_fails` (OKF-native → fail) pin both arms, and `test_audit_migrated_legacy_plan_*` covers the migrated-but-grandfathered arm (OKF-native + grandfathered → warn).

## Contract

REQ-PORT-001: Every plan bundle (under either `docs/plans/<plan-id>/` or `Incubator/<slug>/plans/<plan-id>/`) shall contain the OKF-reserved bundle listing `index.md` at the plan root. `index.md` is a progressive-disclosure listing — a `#` heading followed by `- [child](path) - description` bullets enumerating the bundle members (`plan.md`, `context.md`, `log.md`, `upstream-triage.md`, `findings/`, `reviews/`, `references/`, `diagrams/`, `assets/`, and — **when present** — `plan-retrospective.md`).
**Two rules govern which members are emitted, and they exist because a listing that names an absent file asserts something false** (plan-046 Issue 4.0):
(i) **presence-optional members are emitted only when present.** `plan-retrospective.md` is presence-optional (REQ-PORT-ACT-RETROSPECTIVE), and REQ-PORT-051 already scopes its listing to *"when present"* — so an unconditional entry is a plain implementation bug against a requirement that already reads correctly.
(ii) **subdirectory members are emitted only for directories that EXIST.** Scaffolding the missing ones instead is self-defeating: **git does not track empty directories**, so a scaffolded `diagrams/`/`assets/` vanishes on clone and the dead link returns — and it would generate exactly the `empty-dir` drift `reindex --check` reports (SPEC `REQ-OKF-011`). It **replaces** the legacy `README.md` file-map/reading-order surface (SPEC REQ-OKF-001, OKF-EXTENSION.md §3/§5): the file-map and reading-order content is folded into the listing bullets. Being an OKF **reserved** file, `index.md` carries **no `type` and no `okf_spec`** (SPEC REQ-OKF-031); a bundle-root `index.md` MAY carry `okf_version: 0.2` (SPEC `REQ-OKF-FAM-005`; reconciled from `0.1` by plan-046 Epic 2).
Rationale: `index.md` is the OKF-native entry point for a cold reader — one reserved listing filename at every level of a bundle — and the orientation surface for the folder's contents. Collapsing `README.md` into the reserved `index.md` removes a yf-specific filename in favor of the OKF convention.
The presence + listing-shape check is downgraded to `warn` for an OKF-legacy plan per the OKF-native gate (REQ-PORT-ACT-OKF) and is a hard `fail` only for an OKF-native, non-grandfathered plan — so a migrated grandfathered plan whose `index.md` is still the `README.md` renamed verbatim (not yet a listing) warns rather than fails.
Verification: `plan_manager.py audit` checks `index.md` presence and that its body is a listing (a `#` heading plus child bullets), not the legacy `File map` / `Reading order` headers; the migrate op renames the legacy `README.md` → `index.md` (SPEC REQ-OKF-MIG-005, OKF-EXTENSION.md §1b).

REQ-PORT-002: Every plan folder must contain `context.md` at the plan root with non-empty required sections: Project environment, Tool inventory, Paths, Operator identity, Runtime assumptions.
Rationale: Runtime assumptions and tool versions are load-bearing but never derivable from `plan.md` alone. A cold reader on a different machine needs to know whether the plan is safe to execute as-is.
Verification: `plan_manager.py audit` enforces per-section non-emptiness. Optional sections (Adjacent-concept glossary, Additional context) may be empty.

REQ-PORT-003: `context.md` Tool inventory section must include a snapshot header of the form `<!-- snapshot: host=<hostname> date=<YYYY-MM-DD> -->`. Tool versions are recorded as best-effort; missing tools are `not present`.
Rationale: Tool snapshots are inherently machine-specific. The header tells the cold reader where and when the snapshot was taken so they can judge staleness.
Verification: `_detect_tools` in `plan_manager.py` produces the snapshot header via `_portability_snapshot_header`.

REQ-PORT-004: Every plan must capture its motivation — the "why this exists" — either as a `## Motivation` section in `plan.md` or as a `motivation.md` file at the plan root. Neither may be empty nor contain only the seed placeholder text.
Rationale: The motivating use case is the most-likely-to-be-lost class of context during scope reframings. A cold reader cannot judge a plan's value without it.
Verification: `plan_manager.py audit` checks both locations and rejects placeholder text.

REQ-PORT-005: Every non-exclude row in plan.md's Upstream Issues table must have a corresponding `references/upstream-<N>.md` file containing the full issue body, URL, state, and labels.
Rationale: Upstream issue bodies must travel with the plan folder. `gh issue view` does not resolve across repositories and does not work offline.
Verification: `plan_manager.py audit` counts non-exclude rows and `references/upstream-*.md` files; counts must match.

REQ-PORT-006: The number of `reviews/pass-*.md` files must equal the number of `review:` entry lines in the bundle-root `log.md` — the OKF-reserved update history that **replaces** the legacy in-`plan.md` `**Phase log:**` block (SPEC REQ-OKF-002, OKF-EXTENSION.md §3; see REQ-DATA-012 for `log.md`'s newest-first format). The count-equality invariant **keys on `log.md`'s `review:` lines**; only the file the counter reads moves (`plan.md`'s phase log → `log.md`), the coupling itself is unchanged. `pass-N.md` and its `log.md` `review:` line are written together as a single atomic step **at red-team presentation** (create-on-present, #4), not after the operator resolves concerns. `N` is the review-line count immediately after that line is appended. Because file and line always land together, the count-equality holds *while a plan sits in `review`* with concerns still outstanding — exactly the state the audit must accept as portable.

**Amended (plan-047 Issue 0.9b): the counter shall distinguish a STATUS TRANSITION into
`review` from a RED-TEAM PASS PRESENTATION.** Both emit a `- review:` bullet into `log.md`
today — `update-status <dir> review -m "plan v1 presented"` writes one, and the create-on-present
step above writes another — so a **correct** bundle can show 2 `review:` lines against 1
`pass-1.md` and fail this invariant. Reproduced on a scratch copy, and tripped by this very
bundle during drafting. The two events are not the same event: the status transition happens once
per entry into the `review` phase, while a presentation happens once per red-team cycle.

The invariant is therefore restated as: **`count(reviews/pass-*.md)` shall equal the number of
`log.md` entries recording a red-team PASS PRESENTATION.** A conforming implementation gives the
pass record a distinct marker (or keys the counter on one), so that a phase transition into
`review` is inert to the count in the same way `intake:` and `validated:` already are
(REQ-DATA-012 / REQ-DATA-016). A genuinely missing `pass-N.md` must still fail.
Rationale: the invariant exists to catch a red-team verdict that was never written to disk. A
counter that also counts phase transitions manufactures a failure on a correct bundle — and
because plan-047 Issue 2.5 makes `update-status … approved` *refuse* on a red `ready-check`
(REQ-DATA-028), a bundle that trips the conflation would become unapprovable. The disambiguation
must therefore land **before** that refusal does.
Verification: reproduce the two-lines/one-file state and confirm `_audit_plan` passes; a
genuinely missing pass file still fails.
Rationale: Red-team verdicts degrade to one-line log entries unless captured. Writing at presentation (rather than after resolution) means a plan parked in `review`/REVISE has its verdict on disk, not only in the drafting conversation. Strict correspondence prevents silent loss on REVISE loops. The mandatory red-team **re-run after any major-concern revision** (REQ-PLAN-030 — required now that `ready-for-approval` keys on the *last* verdict being `APPROVE`) is itself a new review cycle: it writes exactly one additional `pass-(N+1).md` + one `review:` line, so the count-equality holds unchanged across the re-run loop. The audit's `_plan_review_line_count` coupling is unchanged in shape: it still counts `review:` lines and compares to `pass-*.md` files — the changes are *when* both are written and *which file* holds the log.
Migration invariant: because the count-equality keys on `log.md`'s `review:` lines, the `**Phase log:** → log.md` extraction must transcribe **every** dated phase-log bullet — each `review:` line included — into `log.md`, preserving the `<status>:` token; it must not collapse the block to a single `scoping:` entry. Extracting only the first `scoping:` date (enough for the grandfather clause, REQ-OKF-MIG-002) would drop the `review:` lines and drive the count to zero against surviving `reviews/pass-*.md` files — a hard fail on a plan that was count-equal before migration. Full-bullet transcription makes the `review:`-line count invariant across migration, so count-equality holds identically before and after (this strengthens the engine's `extract-log` op beyond the first-`scoping:`-date floor of REQ-OKF-MIG-002).
Verification: `plan_manager.py audit` compares `len(glob('reviews/pass-*.md'))` to `_plan_review_line_count`, which counts `review:` entry lines in `log.md` (the source moves from `plan.md`'s phase log; the `^- \d{4}-\d{2}-\d{2} review:` regex rebinds to the `log.md` entry form — see the tension noted at REQ-DATA-012); the vendored `okf.py::migrate` `extract-log` branch transcribes every dated `**Phase log:**` bullet into `log.md` (asserted by `_shared/test_okf.py::test_migrate_extract_log_preserves_all_dated_bullets` and `test_worktree.py::test_audit_migrated_legacy_plan_count_equality_preserved`); SKILL.md Phase 3 Review § "Write the report at presentation" states the `pass-N.md` file + the `log.md` `review:` line are a single atomic step at presentation.

REQ-PORT-008: A `pass-N.md` file is **mutable until resolved, then frozen**. It is written at presentation with a **Resolutions** table — carrying an **`actor`** column recording who resolved each concern (`main-session` under the autonomous default, `operator` under a checkpointed run) — marked `unresolved`; as concerns are resolved the same file is updated in place (rows filled, statuses flipped to `resolved`); once all concerns are resolved the file is frozen and never edited again. A REVISE loop is a new review cycle that produces a new `pass-(N+1).md` at the next presentation — files are updated in place within a cycle, never replaced across cycles. Each full review cycle yields exactly one file. The table was formerly titled *Operator Resolutions*; the rename is required because the resolver is actor-agnostic (REQ-AGENT-043) and a fixed-actor title would misreport an autonomously resolved cycle. The `actor` column carries the information the old title asserted.
Rationale: The portability benefit of #4 is that the verdict exists on disk before resolution; that requires the file to be mutable during resolution. Freezing after resolution preserves the audit trail. "One file per cycle" prevents both silent loss and churn.
Verification: SKILL.md Phase 3 Review § "Update in place on resolution" and "Lifecycle: mutable until resolved, then frozen" subsections; `agents/red-team.md` Rules.

REQ-PORT-007: Plan files may not contain dangling external references. Dangling is defined as: absolute paths matching `/Users/`, `/home/`, `/opt/`, `/var/`, `/tmp/`, `/etc/`, or `C:\`; or parent-traversal `../`. Repo-relative paths (`skills/yf-plan/SKILL.md`) are explicitly allowed. Content inside fenced code blocks and inline code spans is exempt — pattern documentation and command examples legitimately mention such paths.
Rationale: Absolute paths and parent-traversal break the moment a plan folder moves. Repo-relative paths are portable under any repo clone.
Verification: `plan_manager.py audit` greps all plan files after stripping code spans.

## Audit Invariants

REQ-PORT-010: The portability audit is **mechanical only** — file existence, grep, placeholder detection, regex. No semantic evaluation. No LLM calls.
Rationale: Semantic audits are non-deterministic and cannot be version-controlled. Mechanical checks produce the same verdict on the same input forever.
Verification: `_audit_plan` in `plan_manager.py` uses only stdlib (`pathlib`, `re`, `subprocess`) — no external deps beyond click.

REQ-PORT-011: The audit overall status is `pass` iff no finding has status `fail`. Warn findings do not degrade overall status. A `fail` finding halts intake.
Rationale: Two-level severity lets the grandfather clause downgrade without removing the audit entirely.
Verification: `_audit_plan` sets `status = "fail" if any_fail else "pass"`.

REQ-PORT-012: The audit runs as the **last step of Phase 3 (PLAN)**, after red-team approval and before transition to Phase 4 (INTAKE). It is idempotent — safe to run multiple times during plan development. It is a script exit-code check, NOT a bd gate. The term "gate" is reserved for bd gates.
Rationale: The audit validates the planning output, not the intake machinery. Running it at end-of-PLAN lets the operator iterate on gaps (or use `/yf-plan capture`) while still in the planning phase. Idempotency means re-running after fixes is free.
Verification: SKILL.md Phase 3 "Portability audit" subsection contains the audit dispatch snippet; Phase 4 has no audit call; no `bd create -t gate` in the audit path.

## Override

REQ-PORT-020: The operator may bypass the portability audit with an explicit `--force` on approval (e.g., "approve --force"). The override must append a `log.md` entry (SPEC REQ-OKF-002; the reserved update history that replaces the legacy phase log) of the form `- approved: portability audit overridden — reasoning: <operator reason>` under the current `## YYYY-MM-DD` date heading. Unlogged overrides are forbidden.
Rationale: A hard audit with no escape hatch produces operator frustration in legitimate edge cases; an unlogged escape hatch hides quality regressions. Mandatory reasoning gives the audit teeth without blocking operator judgment.
Verification: SKILL.md Phase 3 "Portability audit" subsection documents the override and the phase-log line format.

## Content-fingerprint re-review gate (#64)

REQ-PORT-040: Approval binds to a plan **content fingerprint** — a normalized hash over plan.md's **`## ` content sections only**. The hashed span is the `##` section bodies from **Objective** through **Success Criteria**. The fingerprint **excludes everything before the first `## ` heading** — a single positional rule (SPEC REQ-OKF-010) that subsumes the whole header region: the YAML frontmatter block, every `**Field:**` header line (`Status`, `Epic`, `Fingerprint`, …), and — historically — the in-`plan.md` `**Phase log:**` block. With the phase log relocated to the reserved `log.md` (REQ-DATA-012, REQ-PORT-006) it no longer lives in `plan.md` at all. Consequently the fingerprint is computed over the `##` content sections and is **unaffected by any frontmatter, `**Field:**`, or `log.md` change**: adding the OKF frontmatter block and moving the phase log out are both **hash-neutral by construction** (SPEC REQ-OKF-MIG-003), so a migrated approved plan does not go stale-approved. The hash additionally excludes the `reviews/` directory, the Resolutions tables (formerly *Operator Resolutions*, renamed by plan-045 — the exclusion is positional and unaffected by the title), **and the entire `## Upstream Issues` section** (its "Resolved By" cells are filled at the relocated pour and would otherwise flip the hash mid-execution). The fingerprint is stored under the dual field set (REQ-DATA-015) — the `fingerprint` frontmatter key **and** the `**Fingerprint:**` header line — both above the first `## ` and therefore self-excluded; it is written at APPROVE via the `record-epic` field-insertion mechanism.
Rationale: Approval must bind to *reviewed content*, not survive arbitrary later edits (#64). The "before the first `## `" positional exclusion is exactly what makes OKF frontmatter adoption fingerprint-safe — every metadata surface (frontmatter, `**Field:**` lines, the relocated log) sits above the first `## ` and cannot perturb the hash. The remaining exclusions are the surface that review and pour bookkeeping mutate — hashing them would make the fingerprint self-triggering (a review write or the pour would mark the plan stale against itself).
Verification: `_plan_content_fingerprint` in plan_manager.py drops everything before the first `## ` and hashes the normalized content sections minus the exclusion set; `test_worktree.py` asserts that a review write, a `log.md` write, adding/rewriting the YAML frontmatter block, **and** filling the Upstream Issues "Resolved By" column each leave the fingerprint unchanged.

REQ-PORT-041: A `review`/`approved` plan whose stored `**Fingerprint:**` no longer matches its recomputed content fingerprint is **stale-approved**. `resume-scan` surfaces `stale_approved` as a hard gate at `/yf-plan execute`; `list`/`status` surface it advisorily. A stale-approved plan **cannot execute** until a fresh conformance → red-team → portability cycle re-approves it (re-writing the fingerprint), or the operator passes `--force`, which appends a `log.md` override line stating the reason.
Rationale: A sticky `approved` status let a post-approval scope addition (plan-019) reach execution unreviewed. Binding execution eligibility to the fingerprint forces re-review of any content change; `--force` preserves operator judgment with an audit trail.
Verification: `resume-scan` returns `stale_approved`; SKILL.md §5.2 refuses a stale plan and routes back through review; the `--force` path logs a `log.md` line; `test_worktree.py` covers stale detection and `--force`.

## OKF-PLAN bundle conformance (plan-029)

REQ-PORT-050: Every **non-reserved** `.md` file in a plan bundle shall carry a parseable YAML frontmatter block whose `type` key is non-empty and whose `okf_spec` key is `OKF-PLAN`, placed **above the first `## ` heading**. This is the OKF conformance floor (SPEC REQ-OKF baseline B1/B2 + the `okf_spec` selector REQ-OKF-030) applied to a plan bundle, with the placement rule REQ-OKF-010. The OKF-PLAN `type` assignments are `plan.md`→`Plan`, `findings/*`→`Finding`, `reviews/pass-*`→`Review`, `context.md`→`Environment`, `references/*`→`Reference` (OKF-EXTENSION.md §1/§1a). The two OKF-**reserved** files `index.md` and `log.md` are **exempt** — they carry no `type` and no `okf_spec` (SPEC REQ-OKF-031, REQ-PORT-001, REQ-DATA-012).
Rationale: The single OKF conformance MUST is a non-empty `type` on every non-reserved concept document; the `okf_spec: OKF-PLAN` selector names the composing member so the engine applies the right per-skill ruleset. Above-`## ` placement keeps every added frontmatter block out of the content fingerprint (REQ-PORT-040), so adopting OKF is hash-neutral.
Enforcement gate: the conformance-floor findings (missing frontmatter / `type` / `okf_spec`, and a mis-valued `okf_spec`) are downgraded to `warn` for an OKF-legacy plan and are a hard `fail` only for an OKF-native, non-grandfathered plan, per the OKF-native gate (REQ-PORT-ACT-OKF). This is the documented reconciliation between the literal floor here and the graceful-migration behavior the audit implements: an un-migrated legacy plan (no `plan.md` frontmatter) or a migrated-but-grandfathered plan surfaces its floor gaps as `warn`, never blocking re-audit; a plan that has been made OKF-native and is scoped on/after activation is held to the full floor as a hard `fail`.
Verification: `plan_manager.py audit` (via the vendored `okf.py check_conformance`) flags any non-reserved bundle `.md` missing frontmatter, missing/empty `type`, or missing `okf_spec: OKF-PLAN`, at the OKF-native gate's `okf_missing_level`; migrate assigns each file's `type` per the §1a role→type map (SPEC REQ-OKF-MIG-004), recording any default fallback (`type_source: default-fallback`). Amendment-log entry: root `SPEC.md` `plan-029` (OKF-PLAN adoption — this requirement is added by plan-029 Issue 3.1; the OKF-native gate is documented by Issue 3.6).

## Plan retrospective (plan-045)

REQ-PORT-ACT-RETROSPECTIVE: The `plan-retrospective.md` checks (REQ-PORT-051, REQ-PORT-052) are gated on their own activation marker and are **presence-optional**: the **absence** of `plan-retrospective.md` from a bundle is never a finding of any severity — not `fail`, not `warn`. The file is added to no audit presence list. Only a `plan-retrospective.md` that **exists** is checked, and then only for shape (REQ-PORT-051) and entry fields (REQ-PORT-052).
Rationale: The audit's presence checks are a closed hand-written list, so a new bundle member is a non-event unless it is added to that list — and it must not be. Every one of the pre-existing plan bundles predates this file; a presence check would hard-fail all of them on their next audit for lacking a file that did not exist when they were written. Absence-optional is therefore not a grandfather clause with an expiry but a permanent property: a plan that stopped for no reason and deviated in no way has nothing to record, and an empty retrospective is not more portable than none.
Verification: no `plan-retrospective.md` entry appears in `_audit_plan`'s presence list; a bundle without the file audits identically to one written before this REQ existed.

REQ-PORT-051: When present, `plan-retrospective.md` is a bundle-root OKF-PLAN member carrying `type: Retrospective` + `okf_spec: OKF-PLAN` frontmatter (REQ-PORT-050) and is listed in the reserved `index.md` (REQ-PORT-001). Its body is a sequence of `## RE-NNN` entry sections, each containing a **two-column key/value table**. Entries are append-only and monotonically numbered; `RE-NNN` ids are never reused or renumbered.
Rationale: A two-column table, rather than bold labels, is required because a `**Field:** value` line is invisible to `plan_manager.py audit` yet collides with the reserved-label rule `/yf-okf check` enforces (REQ-OKF-010) — the shape would pass the mechanical audit and fail the conformance check, which is the worst of the two orders to discover. Append-only numbering keeps a `RE-NNN` reference stable from any other artifact that cites it.
Verification: an existing `plan-retrospective.md` parses as `## RE-NNN` sections each holding a two-column table; `/yf-okf check` on a bundle carrying one reports no REQ-OKF-010 label collision and no unregistered-type warning.

REQ-PORT-052: Each `plan-retrospective.md` entry carries the fields `when`, `stop_class`, `asked`, `answered`, `frontloadable`, **`detected_by`**, **`evidence`**, `escape_class`, `adjudication`, `origin`, `culpability`, `prevention`, and `cost`. Entries are of kind **`stop`** or **`deviation`**. `detected_by` is one of `self-report`, `operator`, or `mechanical-check`. `evidence` carries the command and output substantiating any state claim in the entry, or the literal `unverified`. Verbatim quotes and any filesystem path in an entry **must be fenced**.
Rationale: An entry's trust level is a property of who found it, and the recorder is usually the subject — so a retrospective built from an agent's own account would faithfully transcribe a false claim rather than detect one. `detected_by` makes that provenance explicit and `evidence` makes an unsubstantiated claim self-identifying: a state assertion with no evidence is a narration, not a finding. The `deviation` kind exists because the observed incident that motivated these two fields was a **non-stop** — a stop-only schema is blind to exactly the class that autonomy makes more common. Fencing is not cosmetic: an unfenced `/Users/…` path is a hard REQ-PORT-007 dangling-reference failure.
Verification: a written entry contains all thirteen field keys; an entry with an unfenced absolute path fails REQ-PORT-007; `detected_by` and `evidence` are present on every entry regardless of kind.

## Plan escalations (plan-059)

REQ-PORT-ACT-ESCALATION: The `escalations.md` checks (REQ-PORT-053, REQ-PORT-054) are gated on their own activation marker and are **presence-optional**: the **absence** of `escalations.md` from a bundle is never a finding of any severity — not `fail`, not `warn`. The file is added to no audit presence list. Only an `escalations.md` that **exists** is checked, and then only for shape (REQ-PORT-053) and entry fields (REQ-PORT-054).
Rationale: Cloned verbatim from REQ-PORT-ACT-RETROSPECTIVE, and the reasoning transfers without weakening. The audit's presence checks are a closed hand-written list, so a new bundle member is a non-event unless it is added to that list — and it must not be. Every pre-existing plan bundle predates this file; a presence check would hard-fail all of them on their next audit for lacking a file that did not exist when they were written. Absence-optional is a permanent property rather than an expiring grandfather clause, and here it is **stronger** than for the retrospective: a plan that never needed to ask its controller anything has nothing to record, and an empty escalation log is not more portable than none. **The absence of escalations must never be made to look like a defect**, because a system that reports one would create an incentive to manufacture escalations — the Goodhart direction R4 names, in which an agent that can escalate instead of finishing reclassifies difficulty as under-specification.
Verification: no `escalations.md` entry appears in `_audit_plan`'s presence list; a bundle without the file audits identically to one written before this REQ existed — asserted against `plan-050`, which carries 26 real audit findings, so the assertion is not vacuously true over an empty array.

REQ-PORT-053: When present, `escalations.md` is a bundle-root OKF-PLAN member carrying `type: Escalation` + `okf_spec: OKF-PLAN` frontmatter (REQ-PORT-050) and is listed in the reserved `index.md` (REQ-PORT-001). Its body is a sequence of `## ESC-NNN` entry sections, each containing a **two-column key/value table**. Ids are **append-only** and monotonically numbered; `ESC-NNN` ids are never reused or renumbered. Unlike `plan-retrospective.md`, an entry's `state` field is **mutable** — see REQ-PORT-054.
Rationale: The two-column table shape is required for the same reason REQ-PORT-051 requires it: a `**Field:** value` line is invisible to `plan_manager.py audit` yet collides with the reserved-label rule `/yf-okf check` enforces (REQ-OKF-010), so the shape would pass the mechanical audit and fail the conformance check — the worse of the two discovery orders. **The separate file, rather than a new `plan-retrospective.md` entry kind, is the load-bearing decision** (R2): a retrospective entry is a *closed adjudication* written after the fact and is append-only *deliberately*, while an escalation is an *open question* whose whole lifecycle is a state change. Sharing one non-updatable stream would make `retrospective-report` count an unanswered question as a recorded event.
Verification: an existing `escalations.md` parses as `## ESC-NNN` sections each holding a two-column table; `doc_lint --type escalations` reports zero errors on a conforming file; `/yf-okf check` on a bundle carrying one reports no REQ-OKF-010 label collision and no unregistered-type warning.

REQ-PORT-054: Each `escalations.md` entry carries the fields `question`, `alternatives`, `recommended`, `on_no_answer`, `detected_by`, `evidence`, `asked_of`, `state`, and `answer`. `detected_by` is one of `self-report`, `operator`, or `mechanical-check`. `state` is one of `raised`, `answered`, `resolved`, `withdrawn`, and moves only forward through that order. Three constraints are **domain rules, not conventions**:

- **`alternatives` shall carry at least two**, and **`recommended` shall name one of them**. A schema whose `recommended` need not name one of its `alternatives` is not a schema.
- **`on_no_answer` is REQUIRED on every entry.** Fire-and-forget is the actual semantics — no answer-return primitive exists in the herdr channel — so an escalation that omits its own default pretends to a round-trip the transport cannot deliver.
- **An escalation whose recommended default was taken WITHOUT an answer arriving is `resolved`, not `raised`**, with `answer` recording the default that was taken and by whom. Leaving it `raised` would make every fire-and-forget escalation — the ordinary case — trip the close-time open-escalation warning, which would train a reader to ignore that warning.

Rationale: `alternatives` + `recommended` is the dominant operator input measured across the corpus (45 of 119 recorded interactions, the only category present in all seven repositories), and the pre-existing retrospective schema structurally forces it out of the record by storing only the resolution. `recommended` is therefore stored **separately from** `answer`: the two are different facts, and collapsing them destroys the default whenever it is taken. `evidence` defaults to the literal `unverified` rather than to blank, so an unsubstantiated escalation is **self-identifying** — the R4 Goodhart mitigation, alongside `detected_by` being a closed choice. `asked_of` is one of the two seams deliberately left open for a future N-hop generalisation; **no hop counter is seeded**, because the measured topology is depth 1, fan-out 2 and a counter would be machinery built for a topology that does not exist.
Verification: `escalation-raise` refuses to write an entry missing any required field or whose `recommended` is not in `alternatives` (check id `recommended-in-alternatives`); `escalation-resolve` emits `prior_entries_unchanged`, computed from a pre/post hash of the entries it did not touch rather than from its own assertion.


## /yf-plan capture

REQ-PORT-030: `/yf-plan capture [<plan-id>]` is re-entrant, status-agnostic (runs in any phase before intake), and **does not advance plan status**. It does not mutate beads or pour molecules.
Rationale: Capture is a maintenance operation on the plan folder, not a phase transition. Advancing status would conflict with the scoping/investigating/drafting workflow.
Verification: SKILL.md "Phase: CAPTURE (manual)" section explicitly states "does NOT advance plan status"; `/yf-plan capture` path in SKILL.md has no `update-status` call.

REQ-PORT-031: `/yf-plan capture` drafts missing contract files via the captor agent (`agents/captor.md`). The captor is read-only — drafts are returned for operator review and written by the main session only on approval.
Rationale: Mirrors the read-only review-agent pattern (REQ-AGENT-043) and keeps agent scope clean (per REQ-AGENT-050).
Verification: `agents/captor.md` Rules section: "Never write files. The main session writes after operator approval."

REQ-PORT-032: `/yf-plan capture --retro` **extends** (does not replace) folder-state capture by having the captor mine the **current session's conversation** for the seven portability classes: motivation, project environment, adjacent-concept glossary, reviewer verdicts/resolutions, upstream issue bodies, scope-change history, runtime/environment assumptions. Folder state takes precedence; the conversation only fills gaps. The captor remains read-only (REQ-PORT-031 / REQ-AGENT-061).
Rationale: Plans drafted before the portability contract existed, or rescoped mid-draft, carry load-bearing context only in the drafting conversation. `--retro` recovers it into the folder so the plan becomes portable. The seven classes are the recurring categories of conversation-only context.
Verification: SKILL.md Phase: CAPTURE "Retro mode (`--retro`)" enumerates the seven classes and the extends-not-replaces rule; `agents/captor.md` "Retro mode (`--retro`)" section enumerates the same seven classes and stays read-only.

REQ-PORT-033: `--retro` has a hard live-session boundary: it mines only the conversation it is run in and cannot recover a conversation already gone. When the drafting conversation is gone, plain `/yf-plan capture` (folder-state capture) is the fallback. The script-side flag is plumbing only: `plan_manager.py audit --retro` accepts the flag and surfaces it (`"retro"` in JSON output) but does not itself mine — the mechanical audit verdict is identical with or without `--retro`.
Rationale: Retro must not over-promise; a cold reader misled into thinking a gone conversation was recovered is worse than an honest gap. Keeping mining in the agent (not the script) preserves REQ-PORT-010 (the audit stays mechanical, no LLM calls).
Verification: SKILL.md Phase: CAPTURE Retro mode states the live-session boundary and current-session-only Rule; `agents/captor.md` Rules "Retro is current-session only"; `audit` command in plan_manager.py adds `result["retro"]` without altering `_audit_plan`.
